# ADR-1: Архитектура слоя задач

## Статус

Accepted

## Контекст

Изначально вся работа с задачами жила в `TasksViewController` и `CreateTaskViewController`. Контроллеры сами держали массив `[Task]`, сами сортировали и фильтровали, сами проверяли, что у задачи не пустое название, и сами решали что сохранить. Из-за этого:

- невозможно было покрыть юнит-тестами никакую логику кроме UI;
- одно и то же место (валидация названия, выбор приоритета, фильтр "Сегодня") переписывалось два раза в разных экранах;
- любое изменение требований ломало контроллеры целиком.

Нужно было разнести данные, бизнес-логику и UI так, чтобы хотя бы доменные правила можно было тестировать без симулятора.

## Решение

Появились три слоя.

**Модель.** `Task` — обычный `struct` (`Hashable`, `Identifiable`, `Codable`). `TaskPriority` — `enum` с `Int` rawValue. Никакой логики внутри модели нет, она просто хранит поля.

**Domain.**
- `TaskValidator` — проверяет название (не пустое, не длиннее 80 символов) и тримит текст.
- `CreateTaskUseCase` — принимает `CreateTaskInput`, прогоняет через валидатор, собирает `Task`, передаёт в репозиторий. Возвращает `Result<Task, CreateTaskError>`.
- `TaskListProcessor` — берёт `[Task]`, фильтр (`.all/.today/.upcoming`) и сортировку, отдаёт `[TaskSectionResult]`. Для `.upcoming` режима сам группирует по "Эта неделя" / "Этот месяц". Все три параметра инжектятся через протокол `TaskListProcessing`.

**Data.** `TaskRepositoryProtocol` с методами `save / update / delete / fetchAll / addObserver / removeObserver`. Реализация — `InMemoryTaskRepository`, которая хранит массив в памяти и дополнительно пишет/читает его из `UserDefaults` (`SmartPlanner.tasks.v1`), чтобы задачи переживали перезапуск. Все мутации идут через сериальную `DispatchQueue` и нотифицируют подписчиков на main thread.

**Presentation.** Три ViewModel:
- `CreateTaskViewModel` держит черновик задачи, биндится на изменение полей, вызывает `CreateTaskUseCase` по `save()`.
- `TasksViewModel` подписывается на репозиторий, прогоняет данные через `TaskListProcessor`, хранит текущий фильтр и состояние свёрнутых секций.
- `DayTasksViewModel` фильтрует задачи на конкретную дату для экрана выбранного дня.

ViewController'ы теперь делают только три вещи: подписываются на колбэки VM, рендерят, прокидывают пользовательские действия обратно в VM.

## Последствия

**Плюсы.**
- `TaskValidator`, `TaskListProcessor`, `CreateTaskUseCase` — чистые функции/структуры, тесты гоняются мгновенно. Реально покрыты юнит-тестами.
- VM зависят от протоколов (`TaskRepositoryProtocol`, `TaskListProcessing`, `CreateTaskUseCaseProtocol`) — в тестах подменяются стабами и спайами.
- Два экрана (`TasksViewController` и `DayTasksViewController`) разделяют один репозиторий, поэтому изменение задачи на одном экране сразу видно на другом — без ручной синхронизации.
- Поменять "Сегодня" значит обновить одно место в `TaskListProcessor`, UI не трогается.

**Минусы и ограничения.**
- `InMemoryTaskRepository` — синглтон через `static let shared`. Это удобно, но в долгую такой паттерн стоит заменить на нормальный DI.
- Хранение в `UserDefaults` — компромисс. Это не настоящая БД, миграция версий вручную (`v1` в ключе). Для большого количества задач нужно переезжать на Core Data / SwiftData.
- Observer-механизм самописный (`addObserver / removeObserver`). Простой, но если подписчик забывает отписаться — память будет течь. Сейчас все VM делают это в `start/stop`.
- Большая часть VM не привязана к `@MainActor` явно — мы полагаемся на то, что репозиторий нотифицирует на main. Если в будущем появится фоновая загрузка, придётся аккуратно расставлять `@MainActor` или actor-ы.
